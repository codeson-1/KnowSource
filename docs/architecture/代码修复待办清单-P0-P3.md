## P0 — 用户可见 / 数据正确性

### P0-1 前端 SSE `event:error` 被丢弃
- **现象**：LLM 未配置或 provider 不可用时，后端发 `event:error` 后正常 `complete()`，前端只处理 `sources/token/done`，助手气泡卡在「正在生成…」。
- **位置**：`frontend/src/api/chatStream.ts`（dispatch 只认三种事件）、`frontend/src/views/workspace/ChatTab.vue`（`send()` 只在 `onDone` 收尾）。
- **修法**：chatStream 增加 `onError` 回调或 `throw new Error(parsed.message)`；ChatTab 的 catch 中替换 assistant 消息为错误态。可选：后端 error 后补发 `done(refused=true)` 简化客户端状态机。
- **验证**：前端 Vitest 覆盖 error 帧解析（当前无前端测试，见 P2-4）。

### P0-2 publish 无幂等
- **现象**：连点「发布」写多条 PENDING Outbox 事件 → 重复 embedding（浪费 DashScope 配额）+ `vector_store` 无唯一约束会产生重复向量行。ARCHIVED 文档也能重复 publish。
- **位置**：`DocumentService.createPublishEvent()`（只 `requireLatestIngestReady`，不检查是否已 PUBLISHED/SYNCED）。
- **修法**：
  1. publish 前状态前置检查：`if (status=='PUBLISHED' && index_status=='SYNCED') return current;`
  2. 新增迁移 `V10__publish_event_unique.sql`：对 `document_publish_events (doc_id, doc_version, event_type)` 加唯一约束（同文档同版本同类型只允许一条未处理事件）。
- **验证**：后端测试——连续两次 publish 只产生一条事件 / 一次 embedding。

## P1 — 可用性 / 正确性（非用户直接可见）

### P1-1 多轮生成仍用原始问题
- **现象**：`QueryRewriteService` 改写只作用于检索；生成阶段 `answerGenerator.generate(context.question(), ...)` 传原始问题，LLM 可能看到「它的审批流程是什么？」这类缺指代问题。
- **位置**：`ChatService`（检索用 `rewriteResult.retrievalQueries()`，生成用 `context.question()`）、`SpringAiAnswerGenerator`（prompt 无历史、无 rewrittenQuery）。
- **修法**：生成 prompt 使用 rewritten query，或注入最近会话历史；trace 仍展示原始问题。
- **验证**：断言多轮场景下最终 answer 基于改写问题（当前测试只断言 rewrittenQuery + sources）。

### P1-2 解析僵死任务无回收
- **现象**：文档承诺「PARSING > 30min → FAILED」未实现；若 `markIngestFailed` 自身异常，任务停在 PARSING 永不回收。仅 Outbox 索引侧有僵死回收。
- **位置**：`DocumentService`（无 PARSING 超时定时任务）；参照 `DocumentIndexOutboxService.recoverStaleSyncingEvents` 的实现范式。
- **修法**：加 `@Scheduled` 扫描 `ingest_tasks` 中 PARSING 超时的任务置 FAILED。

### P1-3 线程池默认 AbortPolicy（与文档承诺的 CallerRunsPolicy 相反）
- **现象**：`AsyncConfig` 未设 `RejectedExecutionHandler`，队列满时抛异常而非排队/降级。SSE 侧 `ChatService.stream()` 的 `execute()` 未 catch `TaskRejectedException`，高负载可能悬空连接/500。
- **位置**：`AsyncConfig`（taskExecutor 工厂）、`ChatService.stream()`。
- **修法**：显式 `setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy())`（或按用途选策略）；SSE 提交外层 catch 拒绝异常并发 `event:error`。

### P1-4 Eval 指标口径（Recall@5 名不副实）
- **现象**：`EvalRunnerService` 的 recall 实际只判定 `sourceTitles.contains(expectedDocTitle)`，且把同值填给 `recallAt5` 和 `citationHitRate`；`expectedKeywords` 未参与判定。
- **位置**：`EvalRunnerService.toCaseResponse()` / `summarize()`。
- **修法（二选一）**：改名为 `ExpectedDocHit@5`（诚实口径，最小改动）；或让 golden case 校验 retrieved chunk id / keyword，分别算 Recall 与 citation hit。

## P2 — 体验 / 工程化

### P2-1 前端缺 profile / topK / retrievalMode 控件
- **现象**：后端支持这些参数，前端类型已声明但 `ChatTab.vue` 写死 `profile=auto`，请求只传 `question/profile/sessionId`。面试 demo 无法现场切 naive/hybrid/topK。
- **修法**：composer 附近加紧凑控件（profile segmented control、retrievalMode select、topK slider），默认仍 auto/hybrid/5。

### P2-2 Eval 每次运行新建 KB 不清理
- **现象**：`runGoldenSet()` 每次建新 KB + seed + publish，反复运行污染演示数据（KB/文档/向量/QaTrace 累积）。
- **修法**：固定复用一个 `EVAL` KB，或 run 前清理上一轮；至少加命名前缀 + 清理接口。

### P2-3 Eval 报告路径硬编码
- **现象**：`EvalRunnerService` 写死 `docs/eval/report.md`（`REPORT` / `REPORT_PATH`），容器/jar 环境工作目录不定或只读。
- **修法**：配置化 `knowsource.eval.report-path`，默认仍 `docs/eval/report.md`。

### P2-4 前端无自动化测试
- **现象**：`frontend/package.json` 只有 dev/build/preview，SSE 解析、auth refresh、upload/publish 全靠人工验证。
- **修法**：Vitest 覆盖 `chatStream.ts` 的 frame/error/done 解析；Playwright 覆盖 login→upload→publish→chat 主链路。

### P2-5 QaTrace token_usage 空壳
- **现象**：`QaTraceService.record()` 固定写 `token_usage="{}"`，无 token 统计来源。
- **修法**：非流式从 provider response usage 取值；SSE 从最终 chunk/provider 统计补。短期拿不到则文档标「预留字段」（已在文档标注）。
