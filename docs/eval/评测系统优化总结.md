# KnowSource Golden Set 评测系统优化总结

> 优化时间：2026-07-16
> 优化范围：EvalRunnerService、评测指标体系、Faithfulness 自动评测、Golden Set 用例覆盖

---

## 一、系统原状

### 1.1 评测流水线

评测通过 `EvalRunnerService.runGoldenSet()` 执行，流程如下：

1. 加载 `docs/eval/golden-set.jsonl` 中的 21 条用例
2. 自动创建或复用评测知识库（4 篇目标文档 + 8 篇干扰文档）
3. 逐条执行问答并评估
4. 汇总指标，生成 Markdown 报告并覆盖写入 `docs/eval/report.md`

### 1.2 原有指标与判定逻辑

| 指标 | 判定逻辑 | 实际问题 |
|------|---------|---------|
| Recall@5 | `sourceTitles.contains(expectedDocTitle)` | 文档标题命中，非 chunk 级别召回 |
| 引用命中率 | = Recall@5（传同一个值） | 与 Recall@5 完全重复，无独立语义 |
| 拒答准确率 | `outOfScope == refused` | 逻辑正确 |

核心判定逻辑（`toCaseResponse` 原代码）：

```java
boolean citationHit = !goldenCase.outOfScope()
        && goldenCase.expectedDocTitle() != null
        && sourceTitles.contains(goldenCase.expectedDocTitle());
boolean passed = goldenCase.outOfScope() ? refusalCorrect : citationHit && !response.refused();
```

`summarize()` 中两指标共用同一值：

```java
return new EvalSummaryResponse(..., citationRate, citationRate, ...);
```

### 1.3 原有缺陷总结

- **指标语义混淆**："文档命中率""引用准确率""拒答准确率"三项核心指标中，前两项实际是同一个值，简历表述经不起面试深挖
- **Faithfulness 缺失**：完全没有检查 LLM 生成答案是否忠实于检索上下文，一个用例即使模型产生幻觉也会被判通过
- **`expectedKeywords` 已定义但未参与通过判定**：答案答非所问也能通过
- **用例覆盖不足**：21 条用例全部只查 4 篇目标文档，8 篇干扰文档从未被查询，缺少边界条件、否定条件、表格全覆盖等关键场景

## 二、优化一：指标语义修正

### 2.1 改动内容

将三个核心指标重新定义为独立语义：

| 指标 | 旧名称（原代码） | 新名称 | 新判定逻辑 | 衡量维度 |
|------|----------------|--------|-----------|---------|
| `documentHitRate` | `recallAt5` | **文档命中率@5** | `sourceTitles.contains(expectedDocTitle)` | 检索质量——是否找到了正确文档 |
| `citationHitRate` | `citationHitRate`（=recallAt5） | **引用准确率** | `documentHit && keywordHit` | 端到端质量——找到的文档信息是否真正进入了答案 |
| `refusalAccuracy` | `refusalAccuracy` | **拒答准确率**（不变） | `outOfScope == refused` | 安全边界——不该答时不答 |

关键代码变更（`toCaseResponse`）：

```java
// 文档命中：检索阶段，期望文档是否在 Top-5 中
boolean documentHit = !goldenCase.outOfScope()
        && goldenCase.expectedDocTitle() != null
        && sourceTitles.contains(goldenCase.expectedDocTitle());

// 引用准确：端到端，文档命中 且 答案包含期望关键词
boolean citationHit = documentHit && keywordHit;

// 通过判定（不变）
boolean passed = goldenCase.outOfScope() ? refusalCorrect : documentHit && !response.refused();
```

`summarize()` 中两指标独立计算：

```java
long documentHits = results.stream().filter(EvalCaseResponse::documentHit).count();
double documentHitRate = inScope == 0 ? 0.0d : (double) documentHits / inScope;

long citationHits = results.stream().filter(EvalCaseResponse::citationHit).count();
double citationHitRate = inScope == 0 ? 0.0d : (double) citationHits / inScope;
```

### 2.2 影响面

| 文件 | 改动 |
|------|------|
| `EvalSummaryResponse.java` | `recallAt5` 字段更名为 `documentHitRate` |
| `EvalCaseResponse.java` | 新增 `documentHit` 字段，`citationHit` 语义从"文档标题命中"改为"文档命中且关键词命中" |
| `EvalRunnerService.java` | `toCaseResponse()`、`summarize()`、`renderReport()` 全部更新 |
| `frontend/src/types/api.ts` | TypeScript 类型同步更新 |
| `frontend/src/views/workspace/EvaluationTab.vue` | 指标卡片和表格列更新标签文字 |

## 三、优化二：Faithfulness 忠实度自动评测

### 3.1 设计思路

采用 **LLM-as-Judge** 模式，在不阻塞主评测流程的前提下，对每条 RAG 答案进行忠实度后处理评测。

评测流程（两步走）：

```
Phase 1: 遍历 Golden Set → 逐条问答 → 收集 (response, goldenCase) 原始对
Phase 2: 遍历原始对 → FaithfulnessEvaluator LLM 评测 → 构建完整 EvalCaseResponse
```

### 3.2 FaithfulnessEvaluator 核心机制

新文件：`src/main/java/com/knowsource/eval/FaithfulnessEvaluator.java`

```
输入：question（问题）、answer（LLM 回答）、sources（检索上下文）
输出：0.0 ~ 1.0 的忠实度分数

评测步骤：
1. 将回答拆解为独立原子陈述
2. 将检索到的上下文拼给 LLM judge
3. LLM judge 逐一判断每条陈述能否从上下文中推导
4. Faithfulness = faithful_statements / total_statements
```

LLM judge 的 prompt 模板：

```
你是一个忠实的评测裁判。请判断以下回答是否忠实于给定的上下文。

规则：
1. 将回答拆解为独立的原子陈述
2. 对每条陈述，判断它能否从上下文中推导或直接找到依据
3. 如果回答中引用了其他知识来源、编造了数值、或包含了上下文中不存在的事实，则该陈述为不忠实
4. faithful = 所有陈述都忠实的比例

上下文：[检索到的文档片段]
问题：[用户问题]
回答：[LLM 生成的回答]

请仅输出一个JSON对象：
{"faithful": true或false, "score": 0.0到1.0之间的数值, "reasoning": "用中文简述判定理由"}
```

### 3.3 工程决策

- **后处理而非内联**：全部问答完成后统一评测，不阻塞主流程
- **仅评有效用例**：范围外用例、拒答案例、无来源用例跳过（返回 null）
- **LLM 不可用时优雅降级**：`AnswerGenerator` 注入失败时返回 null，报告中显示 "-" 而非报错
- **解析双路径**：完整 JSON 解析优先，正则提取 `"score": x.xx` 降级兜底
- **聚合策略**：对范围内非拒答的所有有效分数取均值

### 3.4 影响面

| 文件 | 改动 |
|------|------|
| `FaithfulnessEvaluator.java` | **新建**：LLM-as-Judge 忠实度评测服务 |
| `EvalRunnerService.java` | 注入 `FaithfulnessEvaluator`，流水线改为两阶段 |
| `EvalSummaryResponse.java` | 新增 `Double faithfulness` 字段 |
| `EvalCaseResponse.java` | 新增 `Double faithfulness` 字段 |
| `EvalRunnerService.renderReport()` | 报告新增「忠实度 (Faithfulness)」指标行和逐用例列 |
| `frontend/src/types/api.ts` | 新增 `faithfulness: number | null` |
| `frontend/src/views/workspace/EvaluationTab.vue` | 新增「忠实度」指标卡片和表格列 |

## 六、后续优化方向

| 优先级 | 优化项 | 说明 |
|--------|--------|------|
| P1 | 评测报告历史存储与趋势对比 | 每次运行归档而非覆盖，支持 A/B 对比和指标趋势图 |
| P2 | Chunk 级别召回评测 | 新增 `expectedChunkIndexes`，引入 ChunkRecall@5 和 ChunkPrecision@5 |
| P2 | Faithfulness 使用全量 chunk 内容 | judge 目前用 snippet（240字符），改用完整 content 提高判定准确度 |
| P2 | Faithfulness 超时与并发控制 | 增加 30s 超时和并发限制，防止单次 LLM 调用阻塞全部评测 |
| P3 | 种子文档版本管理 | KB 描述字段记录种子版本号，内容变更时自动重建 |
| P3 | 配置化 | 报告路径、GoldenSet 路径改为 `application.yml` 配置项 |
| P3 | Answer Relevance 评测 | 复用 LLM-as-Judge 基础设施，新增答案相关性评分 |
| P3 | EvalRunnerService 代码拆分 | 拆出 EvalSeedService 和 EvalReportRenderer |
